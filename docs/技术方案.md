# 微信小程序基础框架技术方案

> 版本：v1.3（2026-08-17）
> 说明：本文档描述**当前框架已实现**的技术方案；具体业务功能（酒店、赛事、餐饮、租赁、商城等）尚未开发，不在本文范围
> 文中已实现能力均对应仓库现有代码；AI 小昭模块（§8）为已确认的技术实现方案，开发时按此执行

## 1. 项目概述

本项目为综合服务类微信小程序的**基础框架**，目标是为后续多业务并行开发提供统一的技术底座：账号体系、请求层、状态管理、微信能力、UI 组件、工程规范一次建设、各业务复用。

当前框架已完成登录闭环（微信手机号快速登录 + 协议勾选 + 登录拦截回跳）与用户资料编辑闭环，并以微信小程序构建（build:mp-weixin）与 vue-tsc 类型检查作为质量门禁。

## 3. 总体架构

### 3.1 分层架构

```
┌───────────────────────────────────────────────┐
│ 页面层  src/pages + src/subpkg-*               │ 只做展示与交互，禁止内联请求
├───────────────────────────────────────────────┤
│ 状态层  src/stores（Pinia）                    │ 跨页面共享状态，storage 持久化
├───────────────────────────────────────────────┤
│ API 层  src/api/*                              │ 按业务域一文件，类型随模块导出
├───────────────────────────────────────────────┤
│ 基础设施  src/utils + src/config               │ request / storage / router / wechat / validate
└───────────────────────────────────────────────┘
```

依赖自上而下单向；基础设施层不感知业务。

### 3.2 分包结构（现状）

**微信约束：tabBar 页面必须在主包；主包与单个分包 ≤ 2M，总包 ≤ 30M。**

```
主包 src/pages/（仅 4 个 tab 页）
├── index/   首页：自定义导航（状态栏适配 + 搜索吸顶）+ banner + 宫格 + 商品流
├── tab2/    分类（占位框架）
├── tab3/    发现（占位框架）
└── mine/    我的：用户卡（头像/昵称/手机号）+ 统计 + 菜单 + 退出登录

subpkg-auth/     登录分包：登录页、用户协议页
subpkg-common/   通用分包：编辑资料页、表单验证演示页
```

**preloadRule**：进入"我的"页时全网络预下载 subpkg-auth。

### 3.3 分包扩展规范（新页面接入）

1. 新页面一律放入分包（按功能域新建 `subpkg-xxx` 目录），**主包不再新增页面**（体积红线）
2. 在 `src/pages.json` 的 `subPackages` 注册；pages.json **禁止写注释**（IDE 按 JSON 校验报错）
3. 跳转一律使用绝对路径：`uni.navigateTo({ url: "/subpkg-xxx/pages/yyy/index" })`
4. 需登录的页面通过 `navigateToNeedLogin` 跳转（见 §5.5），页面内 `onShow` 做未登录兜底
5. 高频入口页可按需在 `preloadRule` 配置分包预下载（预下载总量 ≤ 2M）

## 5. 核心模块设计（已实现）

### 5.1 网络层（src/utils/request.ts）

基于 uni.request 封装，全部请求经 `http` 对象发出：

```ts
import { http } from "@/utils/request";

http.get<UserInfo>("/user/info");                          // 第二参为 query
http.post<LoginResult>("/user/login/wx-mobile", params);   // 第二参为请求体
http.put(...); http.delete(...);
// 第三参为请求选项：{ loading: true }（提交类接口转圈）、{ showError: false }（静默失败）
```

- **响应契约**：后端返回 `{ code, message, data }`，`code === 0` 视为成功（`SUCCESS_CODE`，联调时按后端实际调整）
- **token 注入**：请求拦截自动从 user store 读取 token 注入 `Authorization: Bearer <token>`
- **401 处理**：自动清登录态（store + storage）并 `reLaunch` 登录页，页面无需处理
- **错误分类**：HTTP 状态码错误 / 业务码错误 / 网络层异常三类，统一 reject `RequestError { statusCode, code, message }`，默认自动 toast，页面 catch 只写业务逻辑
- **拦截器扩展**：`useRequestInterceptor(fn)` / `useResponseInterceptor(fn)` 注册全局拦截（token 注入之后的链尾执行）

**api 层规范**：所有接口定义在 `src/api/`（一业务域一文件），类型定义随模块 `export`，页面禁止内联 URL。现有 `api/user.ts` 为标准范式。

### 5.2 登录鉴权

```
微信端：getPhoneNumber 组件回调取 phoneCode + uni.login 取 loginCode
        → POST /user/login/wx-mobile → { token, phone } → userStore.setLoginInfo
前置条件：勾选《用户协议》（自绘圆形勾选框，未勾选 toast 拦截）
存量说明：登录页另含 `#ifndef MP-WEIXIN` 的 H5 演示登录入口（非目标端，仅开发期调试用）
```

- 登录态唯一数据源为 user store，storage 仅作持久化层，页面禁止直接读写 token/phone
- 手机号快速验证组件需**企业认证小程序**并开通（按次收费），个人号不可用——授权拒绝/无权限均有兜底提示

### 5.3 状态管理（src/stores/user.ts，Pinia）

```ts
const userStore = useUserStore();
const { isLoggedIn, maskedPhone, userInfo } = storeToRefs(userStore); // 响应式

userStore.setLoginInfo(token, phone);  // 登录写入（自动持久化）
userStore.setUserInfo(info);           // 缓存用户信息
userStore.setPhone(phone);             // 资料编辑改手机号后同步登录态
userStore.clearLogin();                // 退出 / 401 清除
```

- state 从 storage 启动恢复，getters：`isLoggedIn`、`maskedPhone`（138\*\*\*\*8000 脱敏）
- main.ts 按 uni-app 官方写法注册：`import * as Pinia from "pinia"` + **`return { app, Pinia }`**（必须返回，否则小程序多实例状态不共享）

### 5.4 本地存储（src/utils/storage.ts）

uni-app 无路由守卫，需登录页面统一经封装跳转：

## 8. AI 小昭模块技术方案（智能问答）

> 本模块需接入大模型提供智能问答，前端需要处理流式响应

### 8.1 架构原则：前端绝不直连大模型

小程序代码可被反编译，**大模型 API Key 只能存于后端**。前端仅与自家后端交互，由后端代理大模型：

```
┌────────────┐  HTTPS/SSE   ┌────────────┐  服务商 SDK   ┌──────────┐
│  小程序前端  │ ──────────→ │  后端 AI 网关 │ ──────────→ │  大模型    │
│ (subpkg-ai) │ ←────────── │ (Key/审核/限流)│ ←────────── │ (OpenAI   │
└────────────┘  流式 chunk   └────────────┘  流式转发      兼容协议)  └──────────┘
```

后端代理的四个必然性：**Key 安全**（反编译风险）、**域名白名单**（小程序 request 合法域名需备案可控，大模型服务商域名不可控）、**内容合规**（AI 输出必须审核，见 §8.4）、**计费限流**（用户额度控制只能做在服务端）。

后端接口契约（与后端对齐后落 `src/api/ai.ts`）：

| 接口 | 说明 |
| --- | --- |
| `POST /ai/chat/stream` | 流式问答，`text/event-stream`（SSE）返回增量 |
| `POST /ai/chat` | 非流式降级（一次返回完整回答） |
| `GET /ai/sessions` / `GET /ai/sessions/{id}/messages` | 会话列表 / 历史消息 |

SSE 帧约定：`data: {"delta":"文本增量"}\n\n`，结束帧 `data: [DONE]`。

### 8.2 核心难点：流式响应（uni.request enableChunked）

问答体验的关键是逐字输出。**uni.request 原生支持流式**：`enableChunked: true`（已在 @dcloudio/types 声明）+ 返回的 RequestTask `onChunkReceived` 监听增量——微信端透传底层 `wx.request` 的 `enableChunked`（基础库 ≥ 2.20.1），chunk 回调给 ArrayBuffer。

用法（回调风格拿 task，勿用 await Promise 写法）：

```ts
const task = uni.request({
  url: `${envConfig.baseUrl}/ai/chat/stream`,
  method: "POST",
  enableChunked: true, // 关键：分块传输
  timeout: 120_000,    // 超时是总时长，长回答需调大（见下）
  header: { Authorization: `Bearer ${token}` },
  data: { sessionId, content },
});
task.onChunkReceived((res) => {
  // res.data 为 ArrayBuffer：UTF-8 解码 → SSE 解析 → 取 delta 增量 → 追加渲染
});
// 停止生成：task.abort()
```

**类型缺口（唯一）**：@dcloudio/types 的 RequestTask 接口只声明了 `abort()/onHeadersReceived()`，缺 `onChunkReceived()`（运行时存在）——在项目内补一条声明（如 src/shime-ai.d.ts）或局部断言即可。

两个必处理的边界：

1. **UTF-8 多字节截断**：中文占 3 字节，一个 chunk 可能把字符切成两半——解码优先用原生 `TextDecoder` 的 stream 模式（较新基础库提供，自动缓存不完整字节序列），运行时探测缺失时回退手写状态机（`new Uint8Array(res.data)` 逐字节解析，缓存不完整字节序拼到下个 chunk）。已实现于 utils/ai-stream.ts（双路径）
2. **SSE 分帧**：以 `\n\n` 分帧，`data:` 帧可能同样跨 chunk，解码器需带缓冲拼接

两个必处理的工程细节：

3. **总时长超时**：`timeout` 是**整个请求的总时长**（非空闲超时），模型生成长回答可能超过默认 60s 中途断流——前端显式调大（如 120s），后端保证首 chunk 快速下发（或加心跳帧），避免"已连接但无数据"被判超时
4. **后端网关缓冲**：反代（如 Nginx 默认 `proxy_buffering on`）会把 SSE 全部缓冲后一次性下发，流式退化为假流式——后端需响应 `X-Accel-Buffering: no` 或关闭网关缓冲，这是部署层最常见的翻车点，联调时首先验证

**降级链**：基础库 < 2.20.1 或流式异常 → `POST /ai/chat` 非流式（loading 后一次性展示）。降级收敛在统一的流式工具里（§8.3），页面无感知。

### 8.3 前端实现设计

**目录与分层**（遵循 §3 分包规范）：

```
src/
├── api/ai.ts                  # 接口契约 + 类型（AiMessage / ChatChunk 等）
├── utils/ai-stream.ts         # 流式请求工具（uni.request chunked + UTF-8 解码 + SSE 解析 + abort）
└── subpkg-ai/pages/chat/      # 聊天页（独立分包，注册 subpkg-ai）
```

**流式工具**（`utils/ai-stream.ts`）统一签名，屏蔽平台差异：

```ts
export function streamChat(
  payload: { sessionId?: string; content: string },
  handlers: { onDelta(text: string): void; onDone(): void; onError(err: Error): void }
): { abort(): void };
```

- token 注入复用 user store（与 request.ts 同源）；错误处理独立实现（流式不走 http 封装的一次性 Promise 模型）
- 内部基于 uni.request enableChunked 实现；基础库过低或流式异常时自动降级非流式接口

**api 层**（`api/ai.ts`）：会话/历史等常规接口走 http 封装；流式接口仅声明类型与 URL 常量，实现在 ai-stream.ts

**聊天页 UI 要点**：

- 气泡消息列表（scroll-view + 每次收到 delta 滚动到底部）；流式 append 天然形成打字机效果
- **渲染节流（必做）**：不要每个 delta 都 setData（低端机高频 setData 会明显卡顿）——缓冲增量，每 150ms 左右批量 append 一次，结束时立即 flush；滚动到底同样跟随节流节奏
- 生成中可「停止生成」（abort）、「重新生成」；发送中禁止重复发送
- **Markdown 渲染选型**：大模型输出多为 Markdown——推荐 `mp-html`（小程序富文本组件）+ markdown-it 转换；若首期问答以纯文本为主，可先纯文本展示 + 代码块正则高亮，后续再引入
- 固定展示声明「内容由 AI 生成，仅供参考」（合规要求，见 §8.4）
- 未登录场景：聊天发送前 `navigateToNeedLogin` 拦截（问答记录归属用户）

**会话管理**：后端 `sessionId` 模式（推荐）——上下文由后端拼接，前端只传当前句与 sessionId；本地仅存最近会话列表供快速续聊，Key 在 `StorageKey.AI_SESSIONS` 登记，限制保存条数（如 20 条）。

### 8.4 内容安全与合规（上线硬门槛）

| 事项 | 要求 |
| --- | --- |
| 类目资质 | AI 生成内容需申报对应类目（如 IT 科技/人工智能类），企业主体；提审前向平台确认当前政策 |
| 深度合成备案 | 按《互联网信息服务深度合成管理规定》评估备案义务；选用已完成算法备案的大模型服务商可显著降低门槛 |
| 输入审核 | 后端调微信 `security.msgSecCheck` 检测用户输入（openid 维度） |
| 输出审核 | 模型输出服务端分段审核/抽检 + 服务商自带内容安全能力双保险；命中违规内容不下发前端 |
| 前端声明 | 聊天页固定展示 AI 生成声明；首次进入可弹告知 |

### 8.5 成本控制

- **用户额度**：后端限流（如每用户每日 N 次），额度用尽返回业务码，前端引导次日再来或后续接会员权益
- **上下文窗口**：后端控制携带历史轮数（如最近 10 轮），避免 token 成本随会话无限增长
- **模型分层**：日常问答用高性价比模型；复杂场景（如后续结合业务数据 RAG）再切高级模型，由后端路由

### 8.6 实施步骤

1. 与后端确定大模型服务商与接口契约（SSE 帧格式、错误码、限流码）——联调前置条件
2. `shime-ai.d.ts` 补 RequestTask.onChunkReceived 类型声明 → `utils/ai-stream.ts`（含解码器单测，参照 validate.js 测试模式）→ `api/ai.ts`
3. `subpkg-ai/pages/chat` 聊天页 + pages.json 注册（subpkg-ai 分包）
4. 首页宫格加「AI 小昭」入口 + preloadRule 按需配置预下载
5. 合规四项（§8.4）与后端同步推进
6. 真机验证：流式在开发者工具/iOS/Android 表现差异，重点测中文截断与弱网中断；联调首先验证网关未缓冲（逐字到达而非一次性）

## 9. 风险与已知事项

| 事项 | 影响 | 应对 |
| --- | --- | --- |
| 手机号快速验证需企业认证 + 按次收费 | 登录功能不可用 | 主体认证与开通排期前置；存量 H5 演示登录入口供开发期调试 |
| 后端接口未接入（baseUrl 为占位域名） | 登录/资料等请求报网络错误 | 联调前仅替换 config/index.ts 域名；`{code,message,data}` 契约与 SUCCESS_CODE 需与后端先对齐 |

| pnpm 配置文件被误添加（.npmrc 等） | 构建异常 | README 已注明禁止；code review 把关 |
| AI 小昭类目/备案政策变动 | 提审被拒或下架 | §8.4 合规四项提审前向平台确认；服务商选已备案方 |
